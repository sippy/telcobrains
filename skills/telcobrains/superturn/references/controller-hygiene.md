# Periodic controller audit and resource hygiene

## Five-ST controller audit and cleanup gate

Before entering numbered ST ns, evaluate **ns > 1 && ns % 5 == 1** (ST6, ST11, ST16, ...). A retry/resumption of the same ST is not another ST. Record the boundary and audit receipt idempotently; repeat only if the audited state materially changed. Apply this before successor branch/worktree creation and dispatch, after the predecessor is quiescent and reviewed. Catch up an existing overdue run at its next safe handoff, not by deleting from active lanes.

The controller MUST:
1. Reconcile actual HEAD, accepted candidate, branches/worktrees, active workers/processes/containers, current registry, outstanding gates and next-batch tasks. Check source/build/log bindings and stale or self-reported validation claims. Correct stale controller records rather than copying their assumptions.
2. Inventory older tracked evidence, untracked/ignored logs and artifacts, retired build trees and recovery caches, with paths/sizes, ownership, writer state and keep/delete reasons. Check outside-worktree residue too; a clean Git status is insufficient. Protect active/dirty/WIP trees, unreviewed results, unresolved regressions, required reproducer inputs and unrelated user data.
3. Consolidate useful current state in HEAD: canonical current report, known issues, queued work, reproducible scripts and an evidence index. Remove duplicate, superseded or irrelevant evidence/logs/artifacts from HEAD via a normal reviewed cleanup commit. Never rewrite history, move/delete permanent tags or remove retained refs. Before each tracked removal, verify retrieval of the exact bytes via retained commit/tag plus path, and record that locator in the index. Preserve failure/rejection context and decisive raw evidence historically; do not turn superseded claims into accepted ones by deleting their correction.
4. Remove verified disposable, quiescent, task-owned leftovers from earlier runs. For unique useful untracked evidence, preserve it in Git or an approved durable payload store before cleanup. Prefer recoverable deletion; do not replace clutter with an indefinite duplicate archive. Symlinks/LFS pointers alone are not retained payloads. No blanket git clean, force-removal, shared-source cleanup, ref/history pruning or host-policy changes. Permission/ownership blockers remain explicit with exact paths and recovery owner.
5. Verify the cleanup diff contains no unintended production changes; replay index retrieval and relevant cheap checks; record before/after footprint, removed/retained paths, remaining blockers, exact HEAD and next disposition. Audit is complete only after controller review; block conflicting successor work if required preservation or cleanup is unresolved.

For a large dataset the controller may use a specialized janitor lane when authorized: fresh isolated branch/worktree, local-only execution and the run-authorized toolkit, model and resources, no descendants or model/host/toolkit substitution. Give it an exact allowlist and manifest-first scope. It must not edit live controller state/mainline/other lanes or delete outside its allowlist; it commits an inventory, cleanup proposal/changes and retrieval evidence. The controller owns final acceptance/integration, shared-residue cleanup, refs and dispatch. Carry applicable model, tool and debugging restrictions into its brief. This is an assignment-boundary gate, not a scheduler or authorization to start extra work outside the run.

### All allocated resources, not just Git

At every gate reconcile the complete run-owned resource ledger against live state: worker sessions/jobs, processes/process groups, containers/images/volumes/networks, CPU/GPU reservations and inference jobs, temporary/build/cache directories, mounted filesystems and shared-memory objects, ports/listeners, test services, portals and external payload stores, and any explicitly authorized remote allocations. For each record owner, exact identity/location, active purpose, last user, retention need and retain/release action. Stop/release obsolete task-owned allocations and verify absence or return to the agreed shared baseline; a Git deletion or stopped agent is not resource-release proof. Inspect bindings before deleting an image/volume/network or stopping a shared service: never disrupt shared infrastructure, the Gateway/model server, unrelated work, or another active lane. Use supported lifecycle tools and existing permissions, no remote access or resource escalation merely for cleanup. Mark inaccessible, permission-blocked or unobservable resources UNKNOWN/BLOCKED with a recovery owner, not cleaned. Report residual allocations and before/after disk/resource usage alongside HEAD consolidation. Janitor lanes may inspect/release only explicitly allowlisted task-owned resources; controller reviews the manifest and verifies shared-resource actions.

### Proven ST ownership is mandatory

Cleanup authority covers ONLY data or allocations evidently created by the specific ST being retired/audited (including earlier STs of this same run only when each origin ST is identified). Require creation provenance from the assignment resource ledger, recorded command/output manifest, exact container/job handle or reviewed committed evidence. A matching directory name, UID, timestamp, apparent staleness or proximity to the worktree is not sufficient. Never clean pre-existing/user/shared resources merely because an ST used them. Delete only the proven ST-created data inside a shared store, not the shared store itself. If origin/ownership is uncertain, retain and report UNKNOWN; obtain clarification rather than infer ownership. Janitor allowlists must map every target to its origin ST and evidence of creation.

## Project disk budget: hard cleanup gate

### Allocate before GO

Before substantive work begins, the user assigns a specific project disk budget. Record a positive integer limit_bytes, approving instruction, accounting scope, and measured baseline bytes/time/method in the run manifest. Record an explicit small temporary_overrun_bytes allowance (zero unless approved); never infer unlimited headroom from “slight.” Missing allocation or unresolved accounting blocks GO. This is a project-wide allocation across all lanes and turns, not a fresh allocation per ST, worker or restart. Concurrent runs for the same project share one accounting ledger and budget.

Count the complete agreed project footprint: repository including Git objects and retained history, worktrees, evidence/logs, build outputs, caches/recovery archives, project-owned temporary files, container storage/volumes and external payload copies on every authorized resource. Record absolute roots/storage IDs, shared-storage attribution and exclusions. Pre-existing/shared bytes may count without authorizing their deletion. Use a consistent allocated-byte method; count shared physical storage once where measurable and document hardlinks, reflinks, snapshots, sparse files and shared layers. If attribution is uncertain, agree a conservative accounting method before GO; never silently omit storage. Moving bytes to another directory, archive, host or Git history is not reclamation unless total accounted usage actually falls. Retained copies still count.

### Monitor and reclaim

Measure at startup, progress reviews, before large allocations, every cleanup checkpoint (including ST6/ST11/ST16/... audits), and final closeout. Record usage, headroom and shared-lane reservations; carry them into worker briefs. Reserve or serialize concurrent large allocations so lanes cannot spend the same capacity. Check host free space separately: host pressure may require an earlier stop.

Between cleanups only, usage may temporarily reach limit_bytes plus the approved temporary_overrun_bytes. Record the overrun and next cleanup checkpoint. Before an allocation would exceed that ceiling, or on observing an excess, stop starting disk-growing work and bring cleanup forward. Safely quiesce owned writers and preserve checkpoints; do not continue growing until the fifth-turn boundary. Temporary headroom never becomes a permanent budget increase.

At every cleanup checkpoint, before successor branch/worktree creation or GO:
1. Inventory the full accounting scope; record measured bytes and deficit.
2. Apply the existing provenance, retention and controller-review gates. Reclaim only verified disposable ST-created data. Consolidate HEAD without claiming that removing tracked files also removes retained Git objects.
3. Remeasure after each pass. Make additional bounded passes while identified safe reclamation remains; record targets, actual recovered bytes and residual usage. Do not loop without progress, create indefinite duplicate archives, prune retained history or discard unique evidence merely to meet the budget.
4. PASS only when complete measured usage is at or below limit_bytes, including retained cleanup/report evidence. Record before/after bytes and headroom. Temporary overrun is NOT allowed at cleanup gates or final closeout.

### Required reclamation ladder before escalation

Do not treat one disposable-cache sweep as exhausting cleanup. At cleanup checkpoints proactively inspect both the oldest evidence/logs and the largest allocated-byte consumers, even when usage is currently below the limit. Prioritize meaningful savings rather than repeatedly removing tiny files.

Before asking the user for more space, complete these applicable passes, or record a concrete safety, authority, retention or capacity blocker for each:

1. Rank storage by allocated bytes and age; drill into the largest consumers. Record origin ST, active users/writers, uniqueness, retention requirement, reproducibility/cost of regeneration, present relevance and dependencies. Classify each major item as keep-hot, losslessly archive/compress, redundant, reproducible/disposable, or protected/unknown, with rationale. Age or size alone is never sufficient reason to discard evidence.
2. Release verified disposable outputs and redundant copies under the existing ownership gates. Inspect large build artifacts, caches, container layers and payload copies for actual value and reuse, not just filename or apparent age.
3. Actively losslessly compress/archive cold older evidence and logs where it yields net savings. Use maintained standard archival tools, not a custom format. Preserve exact bytes, paths, provenance and required metadata in an indexed archive; record how to retrieve each item. Test archive integrity and restore/compare retained content before retiring any original copy. For external payloads preserve the required size/digest and durable retrieval reference. Archives must remain in authorized storage and count in the budget.
4. Plan peak scratch space before compression, including source plus archive and verification outputs; use bounded batches within approved headroom and host capacity. Do not destroy the only valid original to make room for its archive. If safe staging is impossible, record that specific blocker. Clean temporary verification copies after successful validation and remeasure actual savings.
5. Re-rank remaining major consumers after each pass and inspect further safe opportunities. Record actions, retrieval checks, before/after totals and why the remaining high consumers cannot safely be reduced. Stop repeating work with no net benefit; already-compressed or incompressible content needs an evidenced skip, not endless recompression.

Archival is not permission to rewrite retained Git history or delete permanent refs. A compressed replacement committed to HEAD may ADD space while old blobs remain reachable; do not report hypothetical Git savings. Remove redundant working copies only after verified historical retrieval under the existing lifecycle. If retained Git storage is the limiting floor, document it and ask for a specific retention-policy decision rather than silently pruning it. A summary alone is not a lossless replacement for required raw evidence.

Escalation is the last resort after applicable safe, authorized reclamation options have been exercised or concretely blocked. A scoped authorized janitor lane may perform this analysis; controller verification remains mandatory. Immediate holds still apply when the ceiling or host safety is threatened: continue bounded reclamation while held, not substantive disk-growing work.

### Hold for the user when cleanup cannot meet the budget

After the reclamation ladder is exhausted or concretely blocked, if safe passes cannot reach the base limit, measurement is incomplete, or required retained history/evidence alone exceeds it, persist BLOCKED_DISK_BUDGET and a project hold. Stop new substantive work and successor creation; safely quiesce affected project writers and retain checkpoints. Bounded cleanup/recovery and controller observation may continue. Timers, completions, retries and restarts must respect the hold and cannot automatically resume substantive work.

Report allocation, measured usage or uncertainty, overage, cleanup passes and recovered bytes, the compression/archival and largest-consumer value reviews, plus exact retained paths/resources and per-option blockers preventing compliance. Ask the user either to raise the allocation to a specific new amount or provide specific further-cleanup instructions. Never raise the budget, broaden deletion scope, offload bytes outside accounting, or delete pre-existing/shared data on your own. Record the user's decision and any authorized retention/scope change; remeasure and clear the hold only when the revised budget is met. Do not send repetitive notifications while waiting.

This is controller-enforced policy, not a provisioned filesystem quota or authority to change host storage policy. For existing runs adopting it, obtain allocation and baseline at the next safe handoff before successor work; do not invent a number or disturb unrelated runs. Editing this protocol does not update running worker briefs automatically.
